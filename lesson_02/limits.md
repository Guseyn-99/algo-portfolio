## 1. Заказы за сутки, `n ≤ 200 000`

Есть ли среди номеров хотя бы два одинаковых?

- **Проходит:** `O(n)`
- **Решение:** Один проход по массиву, хранить уникальные номера в множестве `seen`. Для каждого номера проверяем, есть ли он уже в множестве; если есть — возвращаем `True`, иначе добавляем.
- **Что мешало проще:** Решение с двумя вложенными циклами (`O(n²)`) не проходит, потому что при `n = 200 000` дало бы ~4·10¹⁰ операций, что невозможно.
- **Почему это верно (с числом):** При `n = 200 000` выполняется не более 200 000 итераций, каждая операция с множеством — `O(1)`. Итого ~2·10⁵ операций, что при 10⁷ оп/сек даёт 0.02 секунды — укладывается в ограничение.

## 2. Цены на складе, `n ≤ 100 000`

Найти три самые дешёвые позиции.

- **Проходит:** `O(n log n)`
- **Решение:** Отсортировать список встроенной функцией `sorted()` и взять первые три элемента (срез `[:3]`).
- **Что мешало проще:** Можно было бы найти три минимума за один проход (`O(n)`), но код с сортировкой проще и всё равно проходит, так как при `n = 100 000` время остаётся в пределах нормы.
- **Почему это верно (с числом):** Сортировка `n = 100 000` элементов требует ~ `100 000 * log₂(100 000) ≈ 100 000 * 17 = 1 700 000` операций сравнения. При 10⁷ оп/сек это около 0.17 секунды — приемлемо.

## 3. Архив чеков, `n ≤ 10⁷`, запросов `q ≤ 10⁵`

Отсортирован. По каждому запросу сказать, есть ли такой чек.

> В ответе две величины, а не одна: они растут независимо.

- **Проходит:** `O(q log n)`
- **Решение:** Для каждого запроса выполнить бинарный поиск в отсортированном массиве.
- **Что мешало проще:** Линейный поиск по всему массиву для каждого запроса (`O(n·q)`) дал бы при `n = 10⁷`, `q = 10⁵` — `10¹²` операций, что невозможно. Бинарный поиск значительно быстрее.
- **Почему это верно (с числом):** `log₂(10⁷) ≈ 24`. На все запросы: `q * 24 = 10⁵ * 24 = 2.4·10⁶` операций. При 10⁷ оп/сек это ≈ 0.24 секунды — укладывается.

## 4. Координаты курьеров, `n ≤ 3 000`

Найти двух ближайших друг к другу.

- **Проходит:** `O(n²)`
- **Решение:** Перебор всех пар точек (два вложенных цикла), вычисление манхэттенского расстояния, поиск минимума.
- **Что мешало проще:** Можно было бы использовать алгоритм `O(n log n)`, но при `n = 3 000` квадратичный перебор даёт всего ~4.5·10⁶ операций, что вполне допустимо, а код проще.
- **Почему это верно (с числом):** Количество пар = `n(n-1)/2 ≈ 3000*2999/2 ≈ 4.5·10⁶` операций. При 10⁷ оп/сек это ≈ 0.45 секунды — проходит.

## 5. Одно число `k ≤ 10⁹`

Сколько раз его можно разделить пополам до единицы?

> Вход — одно число, а не список. Проход по всем значениям исключён самим ограничением.

- **Проходит:** `O(log k)`
- **Решение:** Цикл `while k > 1: k //= 2` с подсчётом шагов.
- **Что мешало проще:** Нельзя сделать за `O(1)`, так как число шагов зависит от логарифма `k`. Алгоритм с перебором от 1 до `k` (`O(k)`) недопустим, потому что `k` может быть до 10⁹.
- **Почему это верно (с числом):** `log₂(10⁹) ≈ 30` итераций. Это 30 операций, что при 10⁷ оп/сек даёт пренебрежимо малое время (~0.000003 с) — идеально.

## 6. Две накладные, `n ≤ 10⁵` и `m ≤ 10⁵`

Обе отсортированы. Собрать из них один отсортированный список.

- **Проходит:** `O(n + m)`
- **Решение:** Слияние двух отсортированных списков (алгоритм двух указателей).
- **Что мешало проще:** Простое склеивание и сортировка дало бы `O((n+m) log (n+m))`, что при `n+m = 2·10⁵` даёт около 3.6·10⁶ операций — тоже проходит, но линейное слияние эффективнее и проще.
- **Почему это верно (с числом):** Суммарное число операций = `n + m = 2·10⁵`. При 10⁷ оп/сек это 0.02 секунды — проходит.
